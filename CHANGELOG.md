## 0.2.1 - 2026-10-27

`cpctl` now rides out brief outages instead of failing the step: it retries GitHub OIDC token fetches and control plane requests with backoff on network errors, 429 and 5xx for about half a minute, and keeps sending the current token until its expiry while a refresh fails. A job submission is retried only with the `Idempotency-Key` that `cpctl` sets inside GitHub Actions, so a retry never starts a second job. The guide also shows how to test a deployed control plane on its host before any workflow calls it.


### Fixed

- cpctl retries GitHub OIDC token fetches and repeatable control plane requests with backoff on network errors, 429 and 5xx, keeping the current token until its expiry meanwhile, so a brief outage no longer fails a running job.

### Internal

- The guide shows how to test a deployed control plane on its host with `-insecure-dev-auth`, before any GitHub workflow calls it.
## 0.2.0 - 2026-09-26

The composite action now runs only released binaries: instead of installing Go and building `cpctl` on every step, it downloads the `cpctl` of the release it is pinned to, checks it against the release's `SHA256SUMS` and that it reports that release's version, which takes about a second. Pin it to a release tag, or to the commit SHA a release tag points at; a workflow using `@main`, any other SHA or a local `./action` now fails with an error naming what to pin instead. Workflows pinned to `v0.1.0` are unaffected until they move their pin to this release.


### Changed

- The `action/` composite only downloads the release's `cpctl`, checked against `SHA256SUMS`, instead of building it with Go. It must be pinned to a release tag or the commit SHA a release tag points at; `@main`, other SHAs, `./action` and runners other than Linux x64 or arm64 fail the step.

### Internal

- The example workflow and the docs pin `cloudyhomelab/control-plane/action` to `v0.1.0` instead of `main`.
## 0.1.0 - 2026-09-26

First release of the control plane: a REST API that lets GitHub Actions runners run terraform, packer, ansible or any other command on the host without executing anything themselves. Runners authenticate with their GitHub OIDC token and can only invoke named actions from a YAML catalog, which fixes each command's argv, its typed params, the refs it may run and the claims allowed to call it. The server fetches the code with its own access and runs the exact commit the ref resolved to, chains jobs with `input_from`, and can require a listed approver on the calling workflow's environment. The release ships `controlplane` and `cpctl` for linux amd64 and arm64, and workflows can pin the `action/` composite by tag.


### Added

- A tag-driven release process that publishes version-stamped linux amd64 and arm64 binaries of `controlplane` and `cpctl`, with `controlplane -version` and `cpctl version` to report them.
