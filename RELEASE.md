# Releasing controlplane

Consumers pin this repository by tag: workflows call `cloudyhomelab/control-plane/action@vX.Y.Z`,
which downloads that release's `cpctl`, and hosts install the release binaries. A
tag that moves, or a release whose files change, silently changes what they run. So a
published version is never replaced, only superseded, and three workflows spend most of
their effort refusing to publish. The release itself is one label and two approvals:
nothing typed locally, nothing merged by hand.

## The steps

1. **Land the release summary** through a pull request labelled `prepare-release`, on its
   own or with the last change going in. **Label before merging.** The merge runs
   **Prepare release**, which comments on that PR with the release PR's address, or with
   why it refused.
2. **Approve the release PR.** On its Checks run's summary page, read the brief the
   `Release brief` job wrote, then **Review deployments**, tick `prepare`, **Approve and
   deploy**. The PR merges itself, **Tag release** tags the merge `vX.Y.Z` and comments on
   the PR, and the tag starts the **Release** run.
3. **Approve the publish** on the Release run's summary page, after reading its brief:
   **Review deployments**, tick `release`, **Approve and deploy**. The run's last job then
   downloads the release and checks what a consumer gets.

## Before you start

Once, on the GitHub repository:

- **The GitHub App** whose credentials are the `CLOUDYHOME_BOT_CLIENT_ID` and
  `CLOUDYHOME_BOT_PRIVATE_KEY` secrets, installed with **Contents: write**, **Pull
  requests: write** and **Issues: write** (labels live under Issues). It pushes the release
  branch and the tag and opens the release PR. It has to be a second identity: an event
  caused by the workflow's own `GITHUB_TOKEN` starts no workflow, so a release PR opened with
  it would get no Checks run and a tag pushed with it would start no Release.
- **Two environments, each with a required reviewer**: `prepare`, which holds the release PR
  until someone has read its brief, and `release`, which holds the publish. Without the
  protection rule the job simply runs, so each guard is only as real as its environment.
  Neither may restrict deployment branches: `prepare` is reached from `release/X.Y.Z`
  branches and `release` from a tag.
- **Branch protection on `main` requiring the `all-checks-passed` check.** Auto-merge waits
  on it, and it waits on the `prepare` approval. Without a required check nothing blocks the
  release PR, so Prepare release does not enable auto-merge on it.
- **Allow auto-merge** in the repository settings, with squash allowed.
- **Immutable releases** in the repository settings. GitHub then refuses to move a released
  tag or change a release's files, which turns "never replaced" from a convention into a rule.
- **No ruleset on `v*` tags or `release/**` branches** that the App cannot bypass.
- **The labels** `prepare-release`, and `prepare-release-major`, `-minor` and `-patch` for a
  bump chosen by hand. `prepare-release-X.Y.Z` is created when an explicit version is wanted;
  the `release-X.Y.Z` labels are created by Prepare release itself.

## Changelog fragments

`CHANGELOG.md` is generated by [changie](https://changie.dev) from `.changes/`; never edit it.
Every pull request adds a fragment, created with the pinned changie:

```sh
task changie -- new                                   # prompts for the kind and the text
task changie -- new --kind Fixed --body 'cpctl logs no longer stops at the first empty poll.'
```

The `fragment` job in `check.yml` fails a pull request that adds none, unless it changes a
released version's notes (`.changes/X.Y.Z.md`) instead. `task changelog:check` checks that
fragments parse and that `CHANGELOG.md` is in sync; CI runs it.

| Kind | For | Bump |
| --- | --- | --- |
| `Breaking` | A working caller, catalog or deployment stops working | major |
| `Removed` | Something previously deprecated is gone | major |
| `Added` | A new endpoint, flag, catalog key, param type or action input | minor |
| `Changed` | Behaviour a caller can see, behind a default that keeps today's | minor |
| `Deprecated` | Still works, will not forever | minor |
| `Fixed` | What was wrong, and what it now does instead | patch |
| `Security` | What was exposed and to whom | patch |
| `Internal` | CI, tests, refactors: nothing a caller sees | patch |

## Choosing the version number

[Semantic versioning](https://semver.org). The public API is:

- the HTTP API under `/v1`: paths, request and response shapes, status codes;
- the catalog schema: every key, param type and validation rule;
- the `controlplane` flags and the `cpctl` subcommands, flags and `CONTROLPLANE_*` variables;
- the composite action's inputs and outputs.

A trap worth naming: **tightening a check is breaking** if any existing catalog or call would
now be refused, however wrong it was.

The fragments already say which bump: each kind's `auto` level in `.changie.yaml`, highest
wins. The bare `prepare-release` label takes that bump. A bigger one can be asked for with
`prepare-release-major`, `-minor` or `-patch`, and `prepare-release-1.0.0` names the version
outright; it has to sort above the current one. A smaller bump than the fragments imply is
refused. With no release yet the current version reads as `0.0.0`, so a first release with
an `Added` fragment is `0.1.0` unless you label `prepare-release-1.0.0`.

## The release summary

One paragraph for the release as a whole, in `.changes/unreleased/summary.md`:

```markdown
Adds a directory param type and catalog approvers, and fixes cancel leaving a
terraform child running.
```

It is the first thing a consumer reads, so it lands on `main` through a pull request like
anything else. changie folds it into the version's notes and deletes it. Prepare release
refuses to run without it.

## What Prepare release does

`.github/workflows/prepare-release.yml` runs when a pull request into `main` merges with a
`prepare-release` label. It works from `main`'s tip, since a release folds everything on
`main`, and refuses, quoting the reason on the PR you labelled, if:

- the PR carries more than one `prepare-release` label, or one in a shape it does not know;
- no fragment is waiting, or there is no `summary.md`;
- an explicit version is not above the current one;
- the fragments call for a bigger bump than the label asks;
- the branch `release/X.Y.Z` already exists on `origin`.

Then, on a new `release/X.Y.Z` branch, it runs `changie batch X.Y.Z` (folds the fragments and
summary into `.changes/X.Y.Z.md` and deletes them) and `changie merge` (regenerates
`CHANGELOG.md`), runs the fast gates (format and a version-stamped build), commits
`chore(release): X.Y.Z` as one commit, opens the PR labelled `release-X.Y.Z` with the notes
as its body, enables auto-merge while a required check blocks it, and comments on your PR.

**The release PR is where the notes are read.** A note that reads wrong is fixed where it was
written: close the release PR, delete its branch (`main` is untouched and every fragment
still waits there), fix the fragment through a pull request, and label that PR
`prepare-release`. A release nobody wants is the same PR closed and its branch deleted.

## Approving the release PR

The release PR's Checks run has two jobs no other PR has. **`Release brief`** checks that
the version it adds is the latest in `.changes/` and is not already tagged, checks the
changelog, builds the binaries, and writes the brief: every commit since the previous release
tag with a compare link, the release notes, and the built binaries' checksums. **`Approve the
release`** then waits on the `prepare` environment.

**Read the brief before approving.** Nothing has been tagged yet. The approval is the decision
to release: `all-checks-passed` waits on it, auto-merge waits on that, the merge runs Tag
release, and the tag runs Release. A push to the release branch starts a new Checks run,
which asks again.

To stop a release once its PR is open, close it and delete its branch, or remove the
`release-X.Y.Z` label before the merge: the PR then merges untagged, and Tag release can be
run later from the Actions tab.

## What Tag release does

`.github/workflows/tag-release.yml` runs when a pull request into `main` merges with a
`release-X.Y.Z` label, and works on the merge commit only. It refuses if the PR carries more
than one `release-` label, if the label's version is not the latest in `.changes/` (a release
branch edited after it was labelled, or a label on the wrong PR), if a fragment is still
waiting (a change merged after the release PR opened, which the notes would leave out), or if
`vX.Y.Z` already exists. Then it tags the merge commit `vX.Y.Z` as the App, with the notes as
the tag message, pushes it, and comments on the release PR either way.

Only `v[0-9]+.[0-9]+.[0-9]+` starts Release: a prerelease tag like `v1.0.0-rc1` triggers
nothing.

## Approving the publish

The Release run checks that the tag equals the latest version in `.changes/`, that the
changelog is in sync and that no GitHub release exists for it yet, writes the same brief as
the release PR headed by the tag and its commit, then calls `ci.yml` against the tagged
commit, and then waits on the `release` environment.

**Read the run's summary before approving.** Nothing is published yet, and a tag that never
published can be deleted and moved. Then approve: the publish job builds the binaries with the
version stamped in, checks `controlplane -version` reports it, writes `SHA256SUMS`, and
creates the GitHub release with the notes and every file in `bin/`. The last job, **`Verify
X.Y.Z is downloadable`**, downloads the release on a fresh runner, checks the checksums, and
runs both binaries to confirm they report the version.

Running **Release** from the Actions tab on a branch is a rehearsal: every check and gate
runs and the binaries are built, but nothing is released. The ref decides that, not an input.

## What the workflows check, and why

| Check | Where | Catches |
| --- | --- | --- |
| fragments and a `summary.md` are waiting | Prepare release | a release with no changes, or notes with no opening paragraph |
| the fragments imply no bigger bump than the label asks | Prepare release | a breaking change shipped as a minor |
| `release/X.Y.Z` does not exist | Prepare release | two labelled PRs merged back to back |
| fragments parse, `CHANGELOG.md` is in sync | CI, Release brief, Release | a broken fragment; a hand-edited generated file |
| the version is the latest in `.changes/` | Release brief, Tag release, Release | a release PR or tag for the wrong version |
| no fragment is waiting | Tag release | a change merged after the release PR opened |
| `vX.Y.Z` or its release does not exist | Release brief, Tag release, Release | a version released twice |
| CI against the tagged commit | Release | a green tick on `main` being about whatever `main` was then |
| the binaries report the version, the download matches `SHA256SUMS` | Release | an unstamped build; a release missing a file |

## When something goes wrong

Every later pull request adds a fragment, and a waiting fragment stops Tag release. So a fix
that has to go into `X.Y.Z` after its release commit is on `main` edits `.changes/X.Y.Z.md`
directly and runs `task changie -- merge`, in the same PR, instead of adding a fragment. CI
accepts the changed version file in place of a fragment.

| Situation | What to do |
| --- | --- |
| The summary PR merged without its `prepare-release` label | Run **Prepare release** from the Actions tab; the bump may stay empty. |
| Prepare release refused | Its comment quotes why. Fix it on `main` through a labelled PR, or dispatch Prepare release once fixed. No comment at all means the App's token could not be minted. |
| A change lands on `main` after the release PR opened | Close the release PR and delete its branch, then label the next PR or dispatch Prepare release. |
| The release PR merged but was not tagged | Tag release's comment points at the run. Fix the cause on `main`, then run **Tag release** from the Actions tab, which tags `main`'s tip. |
| Auto-merge was not enabled | Check **Allow auto-merge** and the required check, then `gh pr merge --auto --squash <url>` or merge by hand once approved. |
| A check or gate failed on the Release run | Nothing is published. Fix it on `main`, delete the tag (`git push --delete origin vX.Y.Z`, push access needed), and run Tag release from the Actions tab. |
| The publish step failed | The tag is pushed. Fix the cause, then run **Release** from the Actions tab against the tag. |
| `Verify X.Y.Z is downloadable` failed | The release exists. Look at its files by hand. |
| Released the wrong content or number | Release `X.Y.Z+1` with the correction and say so in its summary. Do not reuse the number. |
